## 结论

官网已经把“看见去向 → 确定眼前目标 → 留断点继续”讲得清楚；扩展也具备这些能力。主要问题是进入真实工具后，导航与操作的优先级又回到了分组、统计和批量恢复，用户需要自行把“当前聚焦”翻译成“最近任务 / 任务工作台”，再理解主题、任务、保存页和断点之间的关系。建议先修整这条主流程的呈现及编辑保护，保留现有视觉体系与底层能力。

没有发现需要推翻现有架构的理由，也没有依据将本轮结果称为“通过可用性测试”。以下结论来自界面与流程检查，不包含真实用户行为研究。

## Findings

### L-01 · P2 · 官网教会的“当前聚焦”，进入插件后没有连续的入口

**用户场景与后果：** 用户在官网试过“注意力地图 → 当前聚焦 → 断点继续”，安装后第一次点工具栏。弹窗默认展示整理当前窗口和应用分组，地图没有直接入口，当前目标藏在第二项“最近任务”；进入完整页又默认是统计式的一周回顾。功能并未缺失，但用户需要重新猜测产品的主线，容易把 Focuence 理解成标签分组器或浏览统计工具，尤其与本轮明确的“地图和聚焦为核心”不符。

**证据：** 本轮 [官网地图](screenshots/website-map-desktop.png)、[官网当前聚焦](screenshots/website-focus-desktop.png)、[弹窗默认页](screenshots/popup-default-400.png)、[完整页默认回顾](screenshots/workbench-default-review.png)。`website/index.html:42` 使用三段体验导航；`popup/app.js:14` 每次初始化为 `groups`，`popup/app.js:149–179` 将当前任务放入“最近任务”；`app/app.js:17`、`:63` 将完整页默认设为回顾，当前任务卡仅由 `renderTasks()` 的 `:382` 渲染。回顾页有最近任务的继续入口，但没有呈现当前窗口绑定的同一块目标状态。任务空态 `app/app.js:385` 还优先让用户“去选择页面”，而上方其实已经支持不选页面直接新建目标。

**建议：** 确立一个贯穿官网、弹窗、侧栏和完整页的可识别入口，例如“当前聚焦”作为入口、“当前任务”作为其中的对象。当前已有目标时，短入口优先露出目标及继续动作；没有目标时，直接提供写下目标的路径。地图在窄载体可跳转到侧栏，不要求把完整地图塞进弹窗。分组、统计、资料与窗口管理继续保留在其适合的位置。

**验收标准：** 从官网进入工具后，用户不需要读仓库说明即可找到同一含义的当前聚焦与地图入口；已有任务时能直接识别正在做什么，没有任务时可先写目标、后关联资料。检查初次打开和重新打开弹窗的状态，不只检查切好标签后的截图。

### L-02 · P2 · 关闭断点编辑器会直接丢弃未保存文字

**用户场景与后果：** 用户被打断前写下进展、卡点和下一步，误按 Escape 或点标题旁的“关闭”。再次进入后只剩旧的已保存值，刚写的线索消失；没有“保留草稿 / 放弃更改”的选择。这发生在产品最需要替用户记住内容的时刻。

**交互与源码证据：** 本轮 [浏览器观察记录](browser-observations.json) 中的 `checkpoint-unsaved-dismissal`：在 popup demo 打开同一任务断点，输入 `未保存草稿核对-20261028`，按 Escape 后重新打开，`progress` 为空，未出现保留或放弃确认。`src/task-memory-ui.js:40–48` 直接关闭对话框，`cancel` 仅在请求进行中阻止关闭；`:50–58` 每次从 `task.checkpoint` 重新构建字段，未设置以任务为键的本地编辑草稿。保存失败时能保留字段，普通关闭却没有同样的保护。侧栏与完整页复用该组件；本轮直接重现的是 popup 等效页，不冒充三端原生安装实测。

**建议：** 保留每个任务的临时编辑草稿，或在有实质更改时明确询问保存、继续编辑或放弃。关闭无改动的编辑器仍应直接退出。不要把未确认的草稿自动写成“已确认断点”。

**验收标准：** 输入唯一测试句后分别用关闭按钮、Escape 退出；再次打开时草稿仍可恢复，或只有用户明确选择放弃才丢弃。覆盖普通留断点、暂停前留断点、切换前留断点及失败重试，并确认保存后的内容仍标为用户确认。

### L-03 · P2 · 任务卡把批量恢复放在单页继续之前

**用户场景与后果：** 用户从任务列表回来，只想打开断点中指定的一页继续写。卡片先出现复用/新开页数及强调的“恢复保存页”，之后才是笔记、目标、确认断点、任务状态与“继续一页”。两种操作都可用，但最突出的动作是重开整组页面，用户更容易走到较重的恢复流程；明确的下一步反而降低了可扫描性。

**证据：** [弹窗任务首屏](screenshots/popup-tasks-400.png) 先展示“恢复保存页”，[滚动到任务动作](screenshots/popup-task-actions-400.png) 后才出现“设为当前任务 / 留断点 / 关联记忆 / 继续一页”；[320 侧栏](screenshots/panel-tasks-320.png) 同样把继续一页放在首屏之外。[完整页回顾](screenshots/workbench-default-review.png) 有足够横向空间，但仍突出恢复保存页。`app/app.js:359–373` 将恢复清单动作放在 `memory.taskActions(task)` 之前，首张任务的恢复按钮使用主要样式；`popup/app.js:74–84` 同样处理。`src/task-memory-ui.js:114–120` 中“继续一页”位于状态、“设为当前任务”、“留断点”和“关联记忆”之后，且是普通样式。当前任务卡的 `:180–181` 已经以单页继续为主要动作，是可复用的正确模式。这里不是要求删除批量恢复，也不是把恢复保存页误认为后台错误。

**建议：** 有可用确认断点时，列表卡依次突出任务名、目标/下一步、继续一页；将“恢复全部保存页（N 页）”与其预览作为明确的次级动作。没有可继续页面时，说明如何关联或选择继续页。展开详情后再处理状态和关联管理，减少一张任务卡承载的并列决定。

**验收标准：** 对同一任务分别准备一个确认继续页和多页保存清单。三端列表的首个主要动作都应能按用户预期回到确认的一页；批量恢复仍可发现，点击前可以看出将涉及多少页面。不能仅用隐藏页数或取消恢复能力来降低密度。

### L-04 · P2 · 主题、任务和原生分组在界面上缺少关系解释

**用户场景与后果：** 官网用“方案写作”“资料研究”这样的工作活动命名地图主题，又在主题旁提供“把当前目标放在这里”。用户容易推断一个主题就是一个任务，或确认某页与任务相关后会改动地图上的主题。真实工具同时存在主题地图、用户任务和浏览器分组，它们的职责不同；如果不解释，用户会把合理的独立状态当成“没有同步”或“分类不准”。

**证据：** [官网地图](screenshots/website-map-desktop.png) 的主题旁紧接目标入口；`website/index.html:45–58`、`:62` 未交代主题与任务的关系。`app/app.js:628–649` 解释了地图的访问方向、次数和时长，但没有解释主题来源、主题不等于任务；`src/task-memory-ui.js:183–188` 的关联说明只覆盖移动/分组，不覆盖主题地图。`docs/DATA_AND_ARCHITECTURE.md:19` 已明确三者分开存储，说明这是界面解释欠缺，而不是建议改变数据架构。

**建议：** 在地图第一次出现、目标入口和关联管理处各放一句与当下操作有关的解释：主题描述浏览内容，任务是用户决定推进的事，分组只整理打开的页面。可以带同一页面的简短例子。地图到任务的入口应说清会创建/切换哪一个对象，不暗示选中主题本身等于开始任务。

**验收标准：** 用户能回答“改任务目标是否会改地图主题”“确认相关是否会把页面移入浏览器分组”“保存页和相关判断是否相同”。这些答案必须能在正在使用的界面中得到，不依赖技术文档；同时保持已确认关联、保存列表和观察到的访问证据的独立性。

### L-05 · P2 · 从所选关系回到路径时，只保留了一个主题，访问事件的两端被拆开

**用户场景与后果：** 用户在地图中选中“视觉创作 → 声音与硬件”，右侧看见 10 月 28 日 09:45 从产品摄影参考切到 ESP32 指南的例证，点击其下的“在路径中回看”，希望核对这次往返。实际进入的路径只筛选“视觉创作”，目标页 ESP32 指南及 09:45 的切换消失，留下更早的摄影记录。时间范围和地图查询参数仍在，但界面失去了这次关系的事件上下文；用户不能沿着地图证据完成回看。

**交互与源码证据：** 本轮 [所选地图关系](screenshots/workbench-map-selected-relation.png) 与 [点击后的路径](screenshots/workbench-path-from-relation.png)，对应 `browser-observations.json` 的 `workbench-map-selected-relation` / `workbench-path-from-relation`。`app/app.js:601–618` 已有 `edge` 与例证，但回看动作只传 `selected.tag`；`:1040` 仅写入 `ui.timelineTag`，`:452–456` 随后过滤掉没有此主题的目标片段。此处不是要求地图推断心理注意力，也不是把没有观察关系的正常空态当成故障。

**建议：** 根据当前对象区分两类入口：选中主题时可以查看该主题的路径；选中关系或具体例证时，应携带两端片段与时间，回到同一范围的路径并定位事件。到达后说明正在回看哪条关系，并保留可返回的上下文。证据过期或不在当前列表时明确说明，不静默退化成一个主题的全部记录。

**验收标准：** 选择跨主题关系后跳转，两端实际页面、事件时刻和先后关系均能被核对；同一关系在不同日期重复出现时可定位选定例证。单独选主题的原有筛选仍可用，返回地图仍保留时间范围与选中关系。

### L-06 · P3 · “暂停”没有说明只解除当前窗口的任务绑定

**用户场景与后果：** 当前任务卡有“暂停”，全局顶部另有暂停记录，任务列表还提供“进行中 / 等待”等状态。用户暂停当前任务后，列表仍显示“进行中”，可能误以为操作没有生效，也可能期待它同时暂停所有浏览记录或改变任务生命周期。

**静态证据：** `src/task-memory-ui.js:55` 使用“暂停当前任务”，`:64–65` 使用“只暂停 / 保存并暂停”，`:178–179` 的当前卡只显示“暂停”。`src/workspace.js:101–120` 的实际操作是令指定窗口的 `taskId` 为 `null`；`src/task-lifecycle.js:3–12` 单独管理生命周期。实现与产品约定一致，问题是界面文案没有把不同影响范围告诉用户。

**建议：** 当前卡使用“暂停此窗口的任务”或在对话框中就近说明“解除此窗口的当前任务；任务仍保留为进行中，浏览记录按记录开关运行”。任务生命周期继续使用明确的状态词，记录开关继续使用“暂停记录”。

**验收标准：** 暂停后反馈包含作用范围，用户能区分窗口当前任务、任务状态和全局浏览记录三个维度；在两个窗口各有任务时，文案与实际结果一致。不要为了文案统一而让暂停操作隐式修改其他窗口或任务状态。

## 已成立的设计约束

- **注意力的解释保持克制。** 官网明确合成示例，注明前台时长不等于实际注意力；完整页用访问先后、观察次数、原始页面与时间提供依据，没有把图的位置当语义距离，也没有制造专注分数。
- **当前意图与生命周期在数据上分开。** 每个窗口有自己的当前任务，任务的“进行中 / 等待 / 已完成 / 已归档”是另一维度。后续应补足文案，而非合并这两个维度。
- **断点来自用户确认。** 最近记录、已确认断点、任务笔记没有被当成同一类内容；没有把系统观察写成用户已完成的进展。
- **局部地图与完整地图有清晰的访问角色。** 侧栏采用局部前后关系，完整页保留所有主题和完整关系表。[侧栏展开后的完整地图](screenshots/panel-map-expanded-workbench.png) 与本轮 `panel-before-map-expansion` / `panel-after-map-expansion` 记录确认：`today`、选中主题“声音与硬件”、关系“视觉创作 → 声音与硬件”都被保留。该 demo 同页交接验证应与尚未验证的原生标签页复用区分。
- **已有当前任务时，侧栏的聚焦卡能正确占据首屏。** [正确复位滚动后的当前任务首屏](screenshots/panel-current-task-first-viewport.png) 已显示目标、“继续一页”和“留断点”，关联页面收起。这是现成的好模式；`L-01` 针对入口、默认落点和跨载体概念连续性，不能误读成“侧栏没有当前任务”或“继续按钮被挤出首屏”。
- **宽窄载体共用语言与样式。** 系统字体、中性表面、少量蓝色选择、文字化时间和可展开的次级信息形成了可延续的体系，无需通过更换视觉语言来解决当前问题。
- **官网没有假装是扩展本体。** 开发预览、源码安装、示例刷新即清空、不会读取标签或历史的说明直接可见；不应为了转化把这些边界隐藏。

## 建议的改进顺序

1. 保护用户刚写下的断点和目标草稿，先避免主流程中的工作损失。
2. 修复地图所选关系到路径的证据交接，使用户可以顺着观察到的关系核对原始事件。
3. 统一从官网到插件的“当前聚焦 / 当前任务”入口关系，明确每个载体的起点。
4. 调整“继续一页 / 恢复保存页”的主次，把确认的下一步放在批量恢复之前。
5. 用就近、短句解释主题、任务与分组，以及窗口暂停与任务状态的区别；不增加长篇教程或新术语。

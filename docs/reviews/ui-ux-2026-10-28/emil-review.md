# Emil 独立评审：前端交互与概念一致性

日期：2026-10-28。源码基准：`bbdac61`，扩展 2.5.0。范围包括官网 `website/`、工具栏弹窗 `popup/`、原生侧栏 `panel/index.html`、完整工作台 `app/`、`options/` 设置入口及其共享 UI 模块。本报告只提出审阅结论，不修改产品、不部署、不提交或推送。

## 方法与判断边界

实际使用 [emil](/Users/aitoshuu/.codex/skills/emil/SKILL.md) 路由，完整读取 [emil-design-eng](/Users/aitoshuu/.cc-switch/skills/emil-design-eng/SKILL.md)，选择其中的组件与交互工艺规范。评审关注：操作后能否立即感到状态变化、连续操作是否保留位置、键盘焦点是否连续、不同入口是否表达同一套对象与动作。未把“加动画”当作目标，也未套用移动原生平台的专属控件要求。

## 结论

现有界面对“前台记录不是实际注意力”“用户确认的断点与系统观察分开”“相关判断与保存页面分开”的事实边界处理得较好。最明显的落差在产品主线：官网已经围绕地图、当前聚焦、断点继续组织体验，扩展的常用入口仍由分组、列表和回顾带路。界面细节的下一步应先改善这种衔接，以及连续操作时的反馈与位置保持。

未发现足以确认的 P1 UI 阻断。下表中的 P2 是影响主线理解或日常连续操作的问题；P3 是可读性或指向性问题，不能据此推断数据错误或效率提升。

## Findings

| 编号 / 优先级 | Before | After | Why |
| --- | --- | --- | --- |
| E1 / P2 | 官网的第一入口是“注意力地图 → 当前聚焦 → 断点继续”；弹窗默认“整理页面”，完整页默认“一周回顾”，地图位于工作台导航靠后位置，聚焦实际藏在任务内。 | 在既有任务、地图架构内，让主要入口明确衔接“看地图 / 当前任务 / 留断点”；辅助整理与资料功能仍保留。官网示例的名称与真实落点直接对应。 | 用户在官网学到的三个动作，安装后需要重新寻找；这是主次与概念映射问题，并非缺少功能。 |
| E2 / P2 | 关联记忆中完成一次纠正后，整个任务对话框被删除重建；嵌套进入断点或关联管理时也没有稳定保留最初的返回点。 | 更新相应行，或恢复同一对象的焦点与滚动位置；离开整条对话流程时回到仍存在的原触发控件。 | “纠正并记住”是高频核心动作，每做一项就重找位置会打断操作，也会影响键盘用户。 |
| E3 / P3 | 从已选关系详情点击“在路径中回看”，只把当前主题传给路径筛选；关系两端与具体访问例证没有成为该动作的目标。 | 明确写成“回看此主题记录”；如入口意图是查看这次关系，则定位现有例证对应的记录，并显示对象与范围。 | 用户正在研究的是具体关系时，进入主题的全部记录仍需再找一遍；按钮应提前说明落点。 |
| E4 / P3 | 官网手机地图的次数、前台时长和来源细节被压到 9–10px，关键解释弱于大号分钟数字。 | 优先减少次要信息与空白，让关系次数、记录口径与页面名称保持可读的正文/辅助字号层级。 | 地图的价值在于理解访问关系及证据口径；没有横向溢出并不等于能轻松读懂。 |
| E5 / P3 | 弹窗的任务筛选和任务状态下拉使用浏览器默认紧凑外观；同一个共享组件在侧栏/工作台采用 32px 控件。 | 为三端共享的下拉建立同一套基础外观，按载体调整密度，保留原生选择与键盘能力。 | 同一对象和状态操作呈现不同工艺层级，让弹窗显得像尚未接入设计系统的临时表单。 |

### E1：官网到扩展的主线需要重新学习

**场景与后果。** 用户在官网写下目标和下一步，再尝试断点继续，随后打开扩展。弹窗首先呈现生成/应用分组；“最近任务”才包含当前任务，且没有直接的地图入口。进入完整页又首先看到七天统计。“当前聚焦”这个名称没有可直接匹配的真实导航项。用户需要理解“聚焦其实是任务里的当前窗口意图”，再寻找操作。

**证据。** `website/index.html:42` 定义三个示例标签；`popup/app.js:14` 默认 `groups`，`:149–179` 才在任务分支渲染当前任务；`popup/app.js:320–321` 的完整回顾入口打开 `review`；`app/app.js:17` 与 `:63` 定义真实导航和默认完整页。新建目标也展示了示例与真实流程的不同：官网 `website/index.html:62` 同时提供目标和下一步并“设为示例目标”，真实 `app/app.js:799–804` / `popup/app.js:91–93` 提供名称、目标、笔记，保存后再显式设为当前任务、另行留断点。这些数据概念本身有必要区分，问题是两边没有把对应关系解释出来。

新截图 [官网聚焦](screenshots/website-focus-desktop.png)、[弹窗默认视图](screenshots/popup-default-400.png)、[弹窗最近任务](screenshots/popup-tasks-400.png)、[320px 侧栏](screenshots/panel-tasks-320.png)、[完整页默认入口](screenshots/workbench-default-review.png) 可直接比较。当前任务为空时，弹窗和窄侧栏先展示恢复保存页，“设为当前任务”在卡片下半部，需要向下滚动才能看到；已有任务与未选择当前意图并存是有效状态，但目前入口没有让选择变轻。旧版任务截图仅作为结构沿革参考，不用它证明当前状态。

**建议与验收。** 明确一套跨载体动作映射，并让用户从打开弹窗/侧栏起能识别当前目标与地图落点；不要求把所有保存动作自动设为当前任务。验收时让首次使用者从官网的三个任务分别找到扩展对应入口，确认“保存任务”“设为当前”“确认下一步”的结果可分辨，且返回提示仍是用户自行启用。

### E2：共享任务对话框在连续纠正后丢失位置

**场景与后果。** 用户进入某个任务的关联记忆，向下核对多条页面并标记相关/不相关。一次操作后，`manager()` 重新构建整个对话框。长列表回到新框的起点，焦点也无法稳定停在刚纠正的对象。另一条路径是“查找结果 → 查看任务 → 留断点”，旧详情框被删除后，关闭断点框无法沿原路径返回。

**实际交互与静态证据。** [浏览器观察](browser-observations.json) 的 `relation-manager-before`、`relation-manager-after-action`、`relation-manager-after-close` 记录主线程通过键盘执行纠正：纠正后焦点是 `memory-close-`，关闭后变为 `BODY`、没有活动控件 ID。`src/task-memory-ui.js:327` 在关联操作后重新调用 `manager()`；`:123–133` 整体生成关联列表；`:41–48` 的 `modal()` 在读取 `document.activeElement` 之前先移除旧 `dialog`，之后仅按记录的 ID 尝试恢复焦点。旧框内按钮和旧框自身已不存在。长列表滚动重置和嵌套详情关闭属于同一重建机制的源码推导，本轮未把这两种额外场景声称为已经独立实测。相比之下，`app/app.js:687–738` 已认真处理主界面的稳定 ID 与焦点恢复，问题集中在这套共享对话框的切换/重建。

**建议与验收。** 保留当前对话流程的外部触发 ID，并在行更新后恢复该对象或下一条合理对象；列表重建时还原滚动偏移。用超过一个视口的合成关联列表，从列表中间连续纠正三项，验证键盘焦点与视口保持在相邻对象；从任务详情进入断点再关闭，验证存在明确返回点，无需从页面顶部重新 Tab。

### E3：关系详情的路径按钮未明确说明会扩大到主题

**场景与后果。** 用户选中“主题 A → 主题 B”的某条关系，读到次数、时间与两端页面后点击“在路径中回看”。落点变为某个主题的记录列表，并非这次关系的访问例证。原来选中的关系还在内存里，但路径页没有显示这个关系上下文，用户很难知道自己当前是在看主题还是关系。

**实际交互与静态证据。** [选中关系](screenshots/workbench-map-selected-relation.png) 显示“视觉创作 → 声音与硬件”、09:45 及摄影参考到 ESP32 文档两端页面；[进入路径后](screenshots/workbench-path-from-relation.png) 只显示“正在回看：视觉创作”，出现该主题的五条记录，目标端 ESP32 文档不在筛选列表中，也没有突出对应例证。`app/app.js:601–618` 在关系详情末尾生成仅带 `data-tag` 的按钮，`:1040` 只设置主题并进入路径；`:452–456` 的实际过滤维度只有状态与主题。所选关系的 `from/to` 仍保留在 URL / 内存里，但不是路径视图的筛选或定位条件。时间范围仍被保留；本项不声称日期交接失败，也不声称访问证据本身错误。

**建议与验收。** 先让按钮文案与当前落点一致。如果保留“回看此主题”的做法，进入后明确主题筛选并提供返回关系上下文；若需要定位关系例证，复用现有访问记录定位能力。验收应同时覆盖一个主题有多个来去方向的情况，确保用户能说清当前列表为何包含这些记录。

### E4：手机地图重要元信息过小

**场景与后果。** 手机访客需要读懂“访问 6 次”“前台 18 分钟”和具体页面线索，才能理解这张图。当前设计优先保持四个节点同时完整呈现，但解释与数字的字号已经接近脚注，分钟大数反而成为最显眼的信息，削弱了“这是访问证据而非注意力评分”的主张。

**证据。** [本轮手机地图截图](screenshots/website-map-mobile.png)；`website/styles.css:1434–1441` 将节点元信息和关系次数设为 9px，`:1372–1376` 将页面次级文字设为 9px；地图口径解释为 `:488–495` 的 10px。没有把字号本身宣称为某个可访问性标准的自动不通过；结论是当前真实尺寸下的相对可读性与信息层级。

**建议与验收。** 让次数、页面名称和“前台记录”口径使用稳定的辅助文字层级，必要时减少同时呈现的细节。320/390 宽度下不用放大即可分辨关系次数与页面线索；放大后仍可操作主题并读到完整解释。不要靠进一步缩小字与增加滚动提示解决。

### E5：弹窗的共享下拉未获得相同基础样式

**场景与后果。** 在“最近任务”中，用户用任务筛选与生命周期状态下拉切换对象。弹窗中两类下拉都表现为紧凑的默认选择框，紧邻带完整边框、留白的按钮和当前任务区。进入侧栏后，相同含义的选择框又变成较高、具有统一圆角和边框的控件。操作仍可用，本项不判为功能阻断。

**证据。** [弹窗最近任务](screenshots/popup-tasks-400.png) 与 [320px 侧栏](screenshots/panel-tasks-320.png)。[浏览器观察](browser-observations.json) 中 `memory-task-filter` 和 `memory-task-status-demo-task-local` 在弹窗测得高度约 20.5px。`src/task-memory-ui.js:116`、`:347` 对两者指定 `standard-select`，但该类的基础控件外观只在 `app/styles.css:87` 定义；`popup/styles.css:1–3` 没有引入该文件，共享 `src/task-memory.css` 也没有此类定义。

**建议与验收。** 把公共选择控件视为一套组件契约，允许弹窗更紧凑，但不要让某一载体直接退回默认样式。对比任务筛选、任务状态、检索范围三种选择控件：高度、字体、焦点、边框和禁用态应有一致关系；400×520 弹窗仍不能挤掉保存动作。没有把桌面控件统一扩大到手机专属触控规格作为要求。

## 跨载体概念与操作一致性

| 概念 | 官网 | 弹窗 / 侧栏 / 完整页 | 判断 |
| --- | --- | --- | --- |
| 地图 | 合成主题、访问箭头、前台时长；明确示例 | 侧栏局部前后关系；完整页按先访问/接着访问排列，附次数、例证与关系表 | 定义一致；示例是一主题一节点的故事图，真实完整图采用访问角色双列，仍需在上手说明中解释两者的视觉差异。 |
| 当前聚焦 | 目标 + 下一步，直接设为示例目标 | 当前窗口任务 + 用户确认断点；任务名称、目标、笔记分开 | 对象划分有依据；入口命名和流程对应不足，见 E1。 |
| 继续 | 恢复本页示例目标与线索，明确不打开真实页 | “继续一页”与“恢复保存页”分开，并展示复用/新开数量 | 值得保留，避免把单页接续与批量恢复揉成一个含糊动作。 |
| 断点 | 一段示例文字 | 进展、卡点、下一步、继续页面；观察记录需用户确认 | 真实端更完整且事实边界正确。官网可简化，但应说明真正的断点如何进入。 |
| 相关 / 保存 | 官网未展示完整机制 | 关联记忆说明相关判断用于识别，保存清单用于恢复 | 定义清楚；连续纠正的交互位置保持仍需完善，见 E2。 |
| 暂停 | 官网说明可暂停记录 | “暂停记录”与当前任务“暂停”独立；生命周期为进行中/等待/完成/归档 | 代码边界合理；相关帮助中应持续保留“窗口意图”与“任务状态”的区分，不能把两类暂停合并。 |
| 数据与设置 | 本机与正常网页请求边界明确 | `options/options.js:1` 进入共享完整设置页；导入预览、普通设置、清理区域分开 | 设置入口共用已有工作台，概念未分叉。本轮未使用真实私人备份执行破坏性清理。 |

## 值得保留的设计

- 石墨正文、蓝色选择与深色主要动作跨端一致，任务内容、证据与操作基本通过排版关系区分。
- 地图选择保持节点位置；完整图保留全部关系表、孤立主题、次数与小样本提示。比为每次选择重新布局更利于对比。主线程实际从侧栏展开地图后，[完整页截图](screenshots/panel-map-expanded-workbench.png) 和 `panel-before/after-map-expansion` 记录确认保留 `today`、当前主题“声音与硬件”以及“视觉创作 → 声音与硬件”关系两端；这条上下文交接值得保留。演示模式在同一页跳转，原生复用标签页的行为仍是源码检查。
- 当前任务把目标、确认断点、继续操作放在一起，观察草稿注明来源时间，没有让模型替用户宣告进展。[侧栏当前任务首屏](screenshots/panel-current-task-first-viewport.png) 确认选定后目标、“继续一页”和“留断点”均在首屏，这个区域的优先级正确，不应为了统一入口而降级；没有拿点击后已滚动的旧截图判断首屏。
- 搜索展示来源、匹配方式、实际时间口径和筛选含义；原文与自己的笔记分开，降低了“资料内容等于用户判断”的混淆。
- 官网标签实现方向键、Home/End 与 roving tabindex；主界面有焦点恢复、对话框和减少动态效果规则。不是需要全面重写可访问性架构的状态。
- 高频列表与地图操作没有引入大范围位移动画。短颜色反馈和静态选择适合当前工作工具，不建议为“精致”统一增加缩放、弹簧或交错入场。

## 未证实或不计入本轮新发现

- 历史四项核心问题未在本报告复述为新发现；本轮 UI 审阅不能证明这些问题已经修复。
- 本轮 demo 创建目标后出现任务计数与列表状态不一致，审阅环境已将其视为演示数据/状态限制；未作为真实扩展缺陷列入。E1 中“仅保存不自动设当前”的事实由真实代码路径支持，不依赖这项 demo 现象。
